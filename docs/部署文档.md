# 轻语（QingYu Care）部署文档

> 适用范围：本文档描述如何从零部署轻语平台（基础设施 + 后端 + 前端 + Widget），以及生产环境的安全与调优要点。
> 本地开发环境搭建请看 [`开发流程文档.md`](./开发流程文档.md)。

## 1. 部署架构总览

```
                       ┌─────────────────────────────┐
  浏览器（管理后台） ──►│  Nginx（静态站 + /api 反代）  │
  客户站点（Widget） ──►│                             │
  第三方服务端 API  ──►└──────────────┬──────────────┘
                                      │ /api
                          ┌───────────▼───────────┐
                          │  后端 Spring Boot     │
                          │  :8080  上下文 /api   │
                          │  （内含 widget.js）    │
                          └───┬───────┬───────┬───┘
                              │       │       │
                    ┌─────────▼─┐ ┌───▼────┐ ┌▼─────────┐
                    │PostgreSQL │ │ RustFS │ │  Redis   │
                    │ pgvector  │ │  (S3)  │ │ 限流/队列 │
                    │ zhparser  │ │ :9000  │ │  :6379   │
                    │  :5432    │ └────────┘ └──────────┘
                    └───────────┘
                              │ OpenAI 兼容协议
                    ┌─────────▼──────────────┐
                    │ 通义千问 DashScope      │
                    │（或任意 OpenAI 兼容端点）│
                    └────────────────────────┘
```

| 组件 | 产物 | 说明 |
|------|------|------|
| 后端 | `backend/target/*.jar` | Spring Boot 可执行 jar，含 Widget 静态资源 `widget.js` |
| 前端管理后台 | `frontend/dist/` | 纯静态文件，由 Nginx（或任意静态服务器）托管 |
| Widget | `backend/.../static/widget.js` | **随后端 jar 发布**，客户站点用 `<script>` 引用，无需单独部署 |
| PostgreSQL 17 | 自定义镜像 `qingyu/pgvector-zhparser:pg17` | 主数据库 + 向量检索（pgvector）+ 中文分词（zhparser） |
| RustFS | 官方镜像 | S3 兼容对象存储，存放知识库原始文档 |
| Redis 7 | 官方镜像 | 限流（Bucket4j）、Webhook 投递队列（Redis Stream）。**可选依赖**：故障时限流 fail-open、队列回退直投，业务不中断 |

## 2. 环境要求

- Docker 与 Docker Compose（基础设施）
- JDK 25+、Maven 3.9+（构建后端）
- Node.js 20+、pnpm 11+（构建前端 / Widget；Vite 7 要求 Node 20 起）
- 通义千问 DashScope API Key（或任意 OpenAI 兼容端点的凭据）

> **只想快速拉起全栈？**跳到 [第 3.5 节「一键容器化部署」](#35-一键容器化部署推荐)，一条命令起五个服务，
> 不必手工构建 jar 与静态文件。要的是**可试用、可截图的演示环境**，看 [第 3.6 节](#36-演示环境部署)。
> 下面第 3~5 节是分组件部署的详细说明，需要精细控制时看。

## 3. 基础设施部署（Docker Compose）

```bash
cd docker
docker compose up -d
```

`docker/docker-compose.yml` 会启动：

| 服务 | 容器名 | 端口 | 说明 |
|------|--------|------|------|
| postgres | qingyu-postgres | 5432 | 首次 `up` 会**本地构建**自定义镜像（编译 SCWS + zhparser，耗时数分钟；国内网络已内置阿里云 apt 源） |
| rustfs | qingyu-rustfs | 9000（S3）/ 9001（控制台） | S3 兼容存储 |
| redis | qingyu-redis | 6379 | 缓存 / 限流 / Webhook 队列 |
| createbuckets | qingyu-createbuckets | - | 一次性任务：创建 `qingyu-care` bucket 后退出 |

首次启动要点：

- `docker/init.sql` 仅在**数据卷首次初始化**时执行：启用 `vector` / `zhparser` 扩展并创建 `chinese_zh` 文本搜索配置。
- 业务表**不在 init.sql 中**，由后端首次启动时 JPA `ddl-auto: update` 自动创建。
- 数据持久化在命名卷：`postgres_data`、`rustfs_data`、`redis_data`。
- **bucket 必须存在**：`x-file-storage` 不会自动建桶，`createbuckets` 这个一次性任务不能省，否则文档上传与聊天附件全部失败。

> ⚠️ **升级到带 zhparser 的镜像后，存量数据卷不会重跑 `init.sql`**——它只在数据目录为空时执行一次。
> 症状是启动日志出现 `混合检索表结构初始化失败，关键词检索可能不可用`，而且是 WARN 不是 ERROR，
> 服务照常起来，只是中文关键词检索与热点分析静默失效。处理方式见[第 10 节「故障手册」](#10-故障手册)第 2 条。

### 3.5 一键容器化部署（推荐）

`docker/docker-compose.prod.yml` 把基础设施、后端、前端编排在一起，一条命令拉起全栈：

```bash
cp .env.example .env      # 填入真实的 DASHSCOPE_API_KEY 与各项凭据
docker compose -f docker/docker-compose.prod.yml --env-file .env up -d --build
```

与开发版 `docker-compose.yml` 的区别：

- 多了 `backend`、`frontend` 两个应用服务（多阶段构建，后端非 root 运行）
- **数据库、Redis、对象存储都不再对宿主机暴露端口**，仅容器网络内可达
- 凭据全部走 `.env`，不写死在文件里
- 所有服务 `restart: unless-stopped`

⚠️ 它声明了独立的项目名 `name: qingyu-care-prod`。**不要删掉这一行**——Compose 默认拿所在目录名（`docker`）作项目名，而两个 compose 文件同在这个目录，不指定的话它们算同一个项目，`postgres_data` 等命名卷会解析成同一批实际卷，生产直接挂上开发库的数据。

验证部署成功：

```bash
docker compose -f docker/docker-compose.prod.yml --env-file .env ps   # 五个服务应全部 healthy
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/            # 前端 → 200
curl -s -o /dev/null -w "%{http_code}\n" http://localhost/api/actuator/health   # 反代后端 → 200
```

再用浏览器直接打开 `http://localhost/knowledge` 并刷新一次——能正常渲染说明 SPA 路由回退配置生效（返回 404 说明 nginx 的 `try_files` 没生效）。

### 3.6 演示环境部署

演示环境 = 上面那套容器化部署 + 激活 `demo` profile。`DemoDataSeeder` 会播种「云舟科技」整套可试用数据：租户/应用/用户、租户级问答策略、知识库 4 篇文档（走真实 `uploadDocument()`，向量可检索）、8 条 QA、12 组铺在最近 30 天的会话、30 天用量与经 `backfill` 真实聚合的分析日表。

```bash
cp .env.example .env
# 编辑 .env：SPRING_PROFILES_ACTIVE=demo，填真实 DASHSCOPE_API_KEY，改掉全部五处 change-me（后端发现遗漏会拒绝启动）
docker compose -f docker/docker-compose.prod.yml --env-file .env up -d --build
docker compose -f docker/docker-compose.prod.yml logs backend | grep 演示数据
```

最后一条应输出「演示数据播种完成」。

**演示账号**（口令写死在 `DemoDataSeeder` 里）：

| 账号 | 口令 | 角色 |
|------|------|------|
| `demo_admin` | `demo123456` | 租户管理员 |
| `demo_agent` | `demo123456` | 坐席，可在人工工作台接管演示数据里那条 `WAITING_AGENT` 的投诉会话 |

平台管理员 `admin` 不由演示数据播种，仍走 `QINGYU_ADMIN_INITIAL_PASSWORD`。

⚠️ **只激活 `demo`，不要写成 `dev,demo`**。本地开发用 `dev,demo` 是为了 SQL 日志与 Swagger，而 `dev` 会打开 Swagger、把 `org.springframework.ai` 调到 DEBUG（完整 prompt 写进日志）、并放开模型端点与 MCP 指向内网——对外可访问的演示环境不该开这三条。`demo` 不依赖 `dev`，单独激活即可。

⚠️ **播种失败是静默的，且重启救不回来**。`DemoDataSeeder.run()` 把异常整个吞掉只记一条 ERROR，应用照常启动（演示数据是旁路不是主链路）。而幂等键是「租户 `demo-cloudboat` 是否存在」——如果播种在建完租户之后才失败（最常见的原因是 `DASHSCOPE_API_KEY` 无效导致文档嵌入失败），重启会直接判定已播种并跳过，留下一份半截数据。处理方式是删掉数据卷重来，不是重启：

```bash
docker compose -f docker/docker-compose.prod.yml --env-file .env down -v
```

**看 Widget 嵌入效果**：`demo-site/` 是配套的「云舟商城」示例站点，README 里那张 Widget 实机图就是在它上面拍的。另起一个静态服务器托管即可：

```bash
npx serve demo-site -l 3000
```

⚠️ 容器化部署时还要把 `demo-site/index.html` 里那行 script 的地址从 `localhost:8080` 改成 `localhost`——prod compose 没把 8080 映射到宿主机，前端 nginx 反代的 `/api` 才是对外入口。细节见 [`demo-site/README.md`](../demo-site/README.md)。

⚠️ **演示应用的 Origin 白名单写死在代码里**：`allowedOrigins` 是 `http://localhost:5173,http://localhost:3000`。Origin 是**协议 + 域名 + 端口**完全一致匹配，所以演示站换了域名**或仅仅换个端口**，widget 都会被开放 API 以 403 拒绝——症状是**客服气泡根本不出现**（拉取 `widget/config` 就被拒，widget 随即停止渲染），界面上没有任何提示，只在浏览器控制台看得到一条 `[Qingyu Widget] 拉取配置失败，停止渲染`。须用 `demo_admin` 登录到「应用管理」把新地址加进「允许来源」。

⚠️ **演示应用的 `appKey` / `appSecret` 是仓库里的固定值**（`demo-cloudboat-shop` 及对应 secret，任何人读代码都能拿到）。演示环境若对公网开放，要么在管理后台重置密钥，要么接受该应用的开放 API 可被任意调用，并把 `rateLimitPerMinute` 调低。

⚠️ 登录 `demo_admin` 后**要在顶部选中「云舟商城客服」应用**——知识库、Prompt 等应用级配置页外面包着 `<RequireApp>`，未选应用时是空状态页。

## 4. 后端部署

### 4.1 构建

```bash
cd backend
mvn clean package            # 含单元测试（纯 Mockito，无需 Docker）
# 或 mvn clean package -DskipTests
```

产物：`backend/target/qingyu-care-*.jar`（Widget 的 `widget.js` 已打包在内）。

### 4.2 环境变量

| 变量 | 默认值 | 必填 | 说明 |
|------|--------|------|------|
| `SPRING_PROFILES_ACTIVE` | 空 | | 激活的 profile。生产留空；演示环境填 `demo`（播种演示数据，见 [3.6](#36-演示环境部署)）。**别在对外环境填 `dev`**，它会打开 Swagger 与 DEBUG 日志 |
| `DASHSCOPE_API_KEY` | - | ✅ | 通义千问 API Key（或兼容端点的 Key） |
| `AI_BASE_URL` | `https://dashscope.aliyuncs.com/compatible-mode/v1` | | 任意 OpenAI 兼容端点，须是完整 base 路径，见下方警示。⚠️ 这是**全局默认**；租户在界面上逐个模型填的端点各家后缀不同，不适用「一律带 `/v1`」 |
| `AI_CHAT_MODEL` | `qwen3.7-flash-2026-07-15` | | 对话模型。**只用于首次启动播种**平台默认对话模型，之后以后台「共享模型」为准 |
| `AI_EMBEDDING_MODEL` | `qwen3.7-text-embedding` | | 向量模型。**只用于首次启动播种**平台默认向量模型（平台还没有任何向量模型时），之后以后台为准，见下方「向量模型」 |
| `AI_EMBEDDING_BASE_URL` / `AI_EMBEDDING_API_KEY` | 空（沿用 `AI_BASE_URL` / `DASHSCOPE_API_KEY`） | | 向量模型用别家时单独指定，同样只用于播种 |
| `AI_EMBEDDING_DIMENSIONS` | `1024` | | 平台统一的向量维度（`vector_store` 列维度）。后台添加的向量模型必须输出这个维度，否则保存时被拒。**上线前定好，不能对已有库热切换**——启动时校验列维度，对不上直接拒绝启动 |
| `REDIS_HOST` / `REDIS_PORT` | `localhost` / `6379` | | Redis 地址 |
| `STORAGE_ENDPOINT` | `http://localhost:9000` | | S3 端点 |
| `STORAGE_ACCESS_KEY` / `STORAGE_SECRET_KEY` | `rustfsadmin` / `rustfsadmin123` | | S3 凭据 |
| `STORAGE_BUCKET` | `qingyu-care` | | S3 bucket |

| `CORS_ALLOWED_ORIGINS` | 空 | | 管理端允许的跨域来源（逗号分隔）。前端与后端同源部署时留空；开放 API 与 widget.js 不受它约束 |

完整模板见仓库根目录的 [`.env.example`](../.env.example)。

> ### ⚠️ `AI_BASE_URL` 必须自带 `/v1`
>
> 正确值：`https://dashscope.aliyuncs.com/compatible-mode/v1`
>
> Spring AI 2.0 起改用官方 openai-java SDK，只往 baseUrl 后拼 `chat/completions` 与 `embeddings`，
> **不再补 `/v1`**（1.x 的 `OpenAiApi` 拼的是 `/v1/xxx`，故当年要求不带，契约已翻转）。
> 缺 `/v1` 会让对话、文档摄取、知识检索**全线 404**。
>
> 这个变量同时喂给 ChatModel 与 EmbeddingModel。从旧版本升级上来的库，`ai_model_config.endpoint`
> 里的存量行还是旧的不带 `/v1` 的 DashScope 值，代码默认值对它们无效，
> 须执行 `backend/src/main/resources/migration/2026-07-30-append-v1-to-model-endpoint.sql`。
>
> ⚠️ **但别把「一律补 `/v1`」当成通则套到 `ai_model_config.endpoint` 上**。那张表里是租户逐个
> 模型填的端点，各家 OpenAI 兼容模式的 base 路径后缀并不统一——智谱是 `/api/paas/v4`、火山方舟是
> `/api/v3`、Gemini 是 `/v1beta/openai`，给它们补 `/v1` 就是 404。判据是「拼上 `chat/completions`
> 之后是否恰好等于该厂商的真实请求地址」，不是「有没有 `/v1`」。上面那个迁移脚本是一次性的历史
> 修补，只针对当年那批 DashScope 行，**别拿它去刷新表**。各厂商的正确端点见后端
> `ModelProviderCatalog`，界面上的提供商下拉就是从它渲染的，选预设不会填错。

> ### 向量模型：后台配置、按应用绑定
>
> 向量模型与对话模型一样在后台管理（「共享模型 / 模型配置」页的「向量模型」标签），环境变量只播种第一条。
> 运维要知道的几点：
>
> - **平台默认** = 启用的平台共享向量模型里优先级数字最小的一条。新应用首次用到知识库时钉住它；之后改平台默认
>   **不影响已有应用**（它们钉的是具体那一行）。
> - **换模型在知识库页按应用进行**，走影子重建：后台用新模型补齐向量，期间检索继续用旧模型，完成后自动切换并清理旧向量；
>   任务进度落库（`embedding_migration_job`），服务重启打断的任务会标为「已中断」，可在界面上继续或取消。
>   同一个模型换托管 / 换 Key（模型 ID 相同）直接生效、不重建。
> - **维度由平台统一**（`AI_EMBEDDING_DIMENSIONS`），添加向量模型时会真实调用一次 embeddings，返回维度不符直接拒绝保存——
>   有的模型不认 `dimensions` 参数、照样返回原生维度（实测 `text-embedding-v1` 返回 1536），所以只信实际返回的长度。
> - **正被应用使用的向量模型不能删除、停用或修改模型 ID**：已有向量按模型 ID 打标，改了会全部检索不到。
> - 租户自带的向量模型端点与对话模型一样经过出站守卫（禁重定向、连接期校验 DNS），见安全基线第 41 条。
> - **只嵌入正文**：向量化的输入只有切块正文，不含 metadata（Spring AI 默认会把文档编号、租户 id 等键值一起嵌入，
>   稀释语义）。**从更早版本升级上来的库，升级后在每个有知识内容的应用的知识库页点一次「重建向量」**——
>   不重建也能检索（同一个模型、同一个向量空间），只是旧向量仍是旧口径。重建逐篇原子替换，期间检索不中断；
>   2026-10-06 实测重建前后分数分布基本不变（相关 0.57~0.92、噪声 0.20~0.35），0.45 无需重标。

> ### ⚠️ 换 embedding 模型后要复核相似度阈值
>
> 相似度阈值的绝对数值只在特定 embedding 模型下有意义，换模型后整个刻度会平移。
> 平台默认 0.45 是按 `qwen3.7-text-embedding` 实测标定的（真实命中 0.57~0.73，无关噪声 0.25~0.30）。
> 沿用旧刻度的症状是**知识库明明有内容、问什么都答不知道**，且全程无异常无日志——
> 检索返回空是正常的 fail-soft 路径。
>
> 现在阈值默认**跟着向量模型走**：每个向量模型带一个「推荐阈值」，问答策略默认跟随它，换模型后不必改策略；
> 只有显式关掉「跟随」的策略（如平台的「严谨投诉处理」固定 0.55）才用自己的值，切换模型时界面会点名提醒。
> 添加别家向量模型时，推荐阈值默认也是 0.45，**这只是起点**，用真实问题测一遍再调，
> 方法见[使用手册第 6 节](./使用手册.md#6-问答策略topk相似度阈值兜底)。

> ### ⚠️ 选向量模型前先实测维度，别假设是 1024
>
> 各家维度差得很远，1024 只是当前默认模型的值。真机实测过一例：火山方舟的 `doubao-embedding-vision` 输出 **2048 维**。
> 后台保存时的探测会挡住不符的模型；想提前确认可以自己打一次 `embeddings` 接口数一下长度：
>
> ```bash
> # 把 <base> / <key> / <模型名> 换成实际值，输出就是该模型的向量维度
> curl -s -X POST "<base>/embeddings" -H "Authorization: Bearer <key>" -H 'Content-Type: application/json' -d '{"model":"<模型名>","input":["测试文本"]}' | python -c "import sys,json; print('维度 =', len(json.load(sys.stdin)['data'][0]['embedding']))"
> ```

数据库连接（`spring.datasource.*`）默认指向 `localhost:5432/qingyu_care`，非本机部署时用 Spring 标准方式覆盖（环境变量 `SPRING_DATASOURCE_URL` / `SPRING_DATASOURCE_USERNAME` / `SPRING_DATASOURCE_PASSWORD` 或外置配置文件）。

### 5.2 Nginx 托管示例

前端是纯静态 SPA，需要把 `/api` 反代到后端，并对 SSE 流式接口关闭缓冲：

```nginx
server {
    listen 80;
    server_name your-domain.com;

    # 管理后台静态站
    root /var/www/qingyu-care/dist;
    index index.html;

    # 知识库文档上传（后端限制单文件 30MB、multipart 32MB），放在 server 级
    # 对所有 location 生效，避免只在 /api/ 里设而漏掉其他上传入口
    client_max_body_size 40m;

    location / {
        try_files $uri $uri/ /index.html;   # SPA 路由回退
    }

    # 后端 API（上下文路径就是 /api，直接透传）
    location /api/ {
        proxy_pass http://127.0.0.1:8080;
        proxy_http_version 1.1;
        # $http_host 带端口、$host 不带：前端不在 80/443 上时（compose 的 FRONTEND_PORT），用 $host 会让后端把
        # 同源请求判成跨域（Origin 带端口、重建出来的地址不带），整个后台登录不了，浏览器只显示「网络错误」
        # （2026-09-30 真机冒烟发现）。客户端能改 Host 但改不了浏览器发跨域请求时的 Host，不构成绕过。
        proxy_set_header Host $http_host;
        proxy_set_header X-Real-IP $remote_addr;
        # ⚠️ 覆盖而非追加（别改回 proxy_add_x_forwarded_for 变量）：后端的 ForwardedHeaderFilter
        # 取 X-Forwarded-For 的「第一段」当客户端 IP，追加模式下第一段是客户端自填的，
        # 登录 / 注册 / 访客的按 IP 限流全部可被伪造 IP 绕过。客户端自带的 Forwarded、
        # X-Forwarded-Port 同理清掉、X-Forwarded-Host 由下面覆盖（Forwarded 的 for= 优先级还高于 XFF）。
        # 前面若还有一层 CDN / 负载均衡，用 realip 模块（set_real_ip_from + real_ip_header）
        # 先把 $remote_addr 还原成真实客户端，别改回追加模式。
        proxy_set_header X-Forwarded-For $remote_addr;
        proxy_set_header Forwarded "";
        # X-Forwarded-Host 由 nginx 覆盖成带端口的真实值，不能只清空：后端的 ForwardedHeaderFilter 一看到
        # X-Forwarded-Proto 就把端口重置成协议默认值，非 80/443 端口下同源请求会被判成跨域（真机冒烟发现）
        proxy_set_header X-Forwarded-Host $http_host;
        proxy_set_header X-Forwarded-Port "";
        proxy_set_header X-Forwarded-Proto $scheme;

        # ⚠️ SSE 必需，不是可选项。流式对话（/api/v1/chat/stream、
        # /api/open/v1/chat/stream）与坐席实时通道都走 EventStream。
        # 开着 buffering 会让 nginx 攒够缓冲区才下发，表现为「回复不逐字出现、
        # 整段一次性刷出」，而且没有任何报错——排查时极难联想到反代配置。
        proxy_buffering off;
        proxy_cache off;
        proxy_read_timeout 3600s;
        chunked_transfer_encoding on;
    }
}
```

> 容器化部署时这份配置已经内置在 `frontend/nginx.conf` 里，随前端镜像一起构建，不必另行维护。

### 5.3 启用 HTTPS

Widget 会被嵌进第三方站点，浏览器对混合内容（HTTPS 页面加载 HTTP 资源）会直接拦截，所以**生产必须上 TLS**。

```nginx
server {
    listen 443 ssl http2;
    server_name your-domain.com;

    ssl_certificate     /etc/letsencrypt/live/your-domain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/your-domain.com/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;
    ssl_ciphers         HIGH:!aNULL:!MD5;
    ssl_session_cache   shared:SSL:10m;
    ssl_session_timeout 10m;

    # 其余 location 配置同 5.2
}

# HTTP 全部跳转到 HTTPS
server {
    listen 80;
    server_name your-domain.com;
    return 301 https://$host$request_uri;
}
```

上了 HTTPS 之后，各租户应用的「Widget 允许来源域名」里也要相应写成 `https://` 开头——Origin 白名单是**协议 + 域名 + 端口完全一致**匹配，写成 `http://` 会导致 Widget 403。

## 6. Widget 部署与接入

Widget 不需要单独部署——`widget.js` 是后端 jar 内的静态资源。客户站点接入：

```html
<script src="https://your-domain.com/api/widget.js?appKey=YOUR_APP_KEY" defer></script>
```

- `appKey` 即管理后台「应用管理」中的 App Key。
- 浏览器侧鉴权走 **Origin 白名单**：必须在应用配置的「允许来源（allowedOrigins）」中加入客户站点域名，否则开放 API 返回 403。
- 服务端集成（非浏览器）则使用 `X-App-Id` + `X-Api-Key` 头调用 `/api/open/v1/**`，超限返回 429 + `Retry-After`。

## 7. 生产环境安全与调优清单

部署到生产前逐项过一遍：

- [ ] **修改全部默认凭据**（PostgreSQL / RustFS / Redis / 平台管理员口令，见第 3 节）。`.env` 里任何一个密钥仍含 `change-me` 时，后端在非 dev/test profile 下**拒绝启动**并在日志里列出变量名（`ProductionSecretsGuard`）。随机值用 `openssl rand -base64 24` 生成。
- [ ] **Redis 密码**：`docker-compose.prod.yml` 要求必须设置 `REDIS_PASSWORD`（没设 compose 直接报错退出），同一个值同时配给 Redis 的 `requirepass` 和后端连接。Redis 里存着限流计数、登录失败计数与 Webhook 投递队列。
- [ ] **自助注册**：默认关闭，租户由平台管理员在后台创建。系统没有邮件/短信验证，开着等于任何人都能无限开租户、各领一份免费额度。演示环境确需开放时设 `SELF_REGISTER_ENABLED=true`，或平台管理员在「平台配置 → 开放注册」里打开（后者优先）。
- [ ] **登录防爆破**：基线已开——每 IP 每分钟 20 次登录 / 5 次注册，同一账号连续输错 5 次锁定 15 分钟（`qingyu.care.auth.*`）。依赖 Redis，Redis 不可用时放行；反代后面务必用 `$remote_addr` **覆盖**（而非追加）`X-Forwarded-For` 并清空客户端自带的 `Forwarded`（照抄上面的 nginx 样例即可）：不传则所有人共用反代的 IP、一起被限流；用追加模式则客户端可伪造 IP，限流形同虚设。前面还有 CDN / 负载均衡时用 nginx realip 模块先还原真实客户端地址。
- [ ] **平台管理员口令**：用 `QINGYU_ADMIN_INITIAL_PASSWORD` 指定，或首启后立刻用启动日志里打印的随机口令登录并修改。
- [ ] **跨域**：管理前端与后端同源部署时 `CORS_ALLOWED_ORIGINS` 留空（管理端拒绝一切跨域）；前端单独部署到别的域名才填。`sa-token.is-read-cookie` 保持 `false`。
- [ ] **Webhook 回调地址**：只接受公网 http(s)，指向内网/环回会在保存时被拒；`qingyu.care.webhook.allow-private-targets` 生产必须是 `false`（它只给本地联调与集成测试用）。
- [ ] **模型端点**：租户填的 endpoint 同样只接受公网 http(s)；`MODEL_ALLOW_PRIVATE_ENDPOINTS` 生产保持 `false`（只有本机跑自托管模型的开发环境才打开）。
- [ ] **登录态时长**：`sa-token.timeout` 7 天、`active-timeout` 12 小时、`is-share: false` 是基线；别为了省事改回 30 天 / 永不过期。
- [ ] **收紧端口暴露**：5432 / 9000 / 9001 / 6379 不对公网开放（compose 里改为仅绑定内网，或删掉 `ports` 走容器网络）。8080 只经 Nginx 反代访问。
- [ ] **启用 HTTPS**：Widget 嵌入第三方站点、开放 API 签名头都应走 TLS。
- [ ] **RustFS bucket 保持私有**：`qingyu-care` 默认就是私有的，**不要**给它开匿名读。聊天附件与知识库原文都在里面，一律经带鉴权的代理端点下发；开了公共读等于把所有租户的文档暴露给知道对象名的人。
- [ ] **日志级别**：基线已是 `INFO`（`dev` profile 才是 DEBUG）；`org.springframework.ai` 的 DEBUG 会把完整 prompt 写进日志，生产别开。
- [ ] **确认没有激活 `dev` profile**：Swagger（`/api/swagger-ui.html`、`/api/v3/api-docs`）、`/actuator/metrics` 与 DEBUG 日志都只在 `dev` 下打开，基线配置全部关闭。dev 还会打开自助注册、放开模型与 MCP 指向内网，并跳过上面的占位符密钥检查。确认方法：`docker compose -f docker/docker-compose.prod.yml exec backend env | grep SPRING_PROFILES_ACTIVE` 应为空或只有 `demo`。
- [ ] **限流与额度**：开放 API 默认每应用 60 次/分钟（`qingyu.care.openapi.default-rate-limit-per-minute`，应用级可覆盖）；租户月度额度按套餐（FREE/PRO/ENTERPRISE）生效，超额 403 `QUOTA_EXCEEDED`。
- [ ] **知道 Redis 的降级语义**：Redis 故障时限流放行（fail-open）、Webhook 队列回退 `@Async` 直投、DB 重试扫描兜底——业务不中断，但限流失效期间需关注上游告警。
- [ ] **Webhook 出网**：后端需能访问租户配置的回调地址；投递签名头为 `X-Qingyu-Signature: sha256=...`，值是 `HMAC-SHA256(secret, "<X-Qingyu-Timestamp>.<原始请求体>")` 的十六进制。接收方要做三件事：用同法复算并比对签名；拒绝 `|now - X-Qingyu-Timestamp| > 5 分钟` 的请求（防重放）；按载荷 `id` 去重（投递是至少一次，重试复用同一个 id）。退避重试参数见 `qingyu.care.webhook.*`。
- [ ] **依赖漏洞扫描**：发版前跑一次 `NVD_API_KEY=xxx ./scripts/dep-audit.sh`（后端 OWASP dependency-check + 三个 pnpm 项目的 `pnpm audit`）。仓库没有 CI，这一步只能手动；NVD key 免费申请。
- [ ] **上传与摄取上限**：知识库单文件 30MB、抽取正文 200 万字符、单文档 2000 块；附件单会话 20 个、孤儿 2 小时清理。数字都在 `application.yml` 的 `qingyu.care.knowledge.*` / `qingyu.care.attachment.*`，按套餐调整时三处（后端 multipart、nginx `client_max_body_size`、这里）要一起改。
- [ ] **`ddl-auto: update` 的边界**：只增不删（不会删列/删表/收窄类型），大版本升级前仍应先备份再启动新版本。

## 8. 备份与升级

### 备份

```bash
# 数据库逻辑备份（推荐纳入定时任务）
docker exec qingyu-postgres pg_dump -U postgres qingyu_care > backup_$(date +%F).sql

# 对象存储：备份 rustfs_data 卷，或用 mc mirror 同步到异地
docker run --rm -v qingyu-care-prod_rustfs_data:/data -v $(pwd):/backup alpine \
  tar czf /backup/rustfs_$(date +%F).tar.gz -C /data .
```

**要备的是两份，不是一份**：数据库里有文档记录与向量，对象存储里有原始文件。只备数据库的话，恢复后文档列表都在、点开下载全部 404；只备对象存储则等于什么都没有。

向量数据在 `vector_store` 表内，逻辑备份已覆盖，不必单独处理。

### 恢复演练

**只写备份不写恢复的备份方案等于没有。**至少演练一次，确认备份真的能用：

```bash
# 1. 起一个临时库（不要往生产库上恢复）
docker run -d --name pg-restore-drill \
  -e POSTGRES_PASSWORD=drill -e POSTGRES_DB=qingyu_care \
  qingyu/pgvector-zhparser:pg17

# 2. 等就绪后建扩展（备份文件里通常不含 CREATE EXTENSION 的权限语句）
sleep 15
docker exec -i pg-restore-drill psql -U postgres -d qingyu_care -c \
  "CREATE EXTENSION IF NOT EXISTS vector; CREATE EXTENSION IF NOT EXISTS zhparser;"

# 3. 恢复
docker exec -i pg-restore-drill psql -U postgres -d qingyu_care < backup_2026-08-11.sql

# 4. 验证：三个数字都不该是 0
docker exec -i pg-restore-drill psql -U postgres -d qingyu_care -c \
  "SELECT (SELECT count(*) FROM sys_tenant) AS 租户数,
          (SELECT count(*) FROM document WHERE status='COMPLETED') AS 已完成文档数,
          (SELECT count(*) FROM vector_store) AS 向量数;"

# 5. 收工
docker rm -f pg-restore-drill
```

第 4 步的**向量数**尤其要看：它是「知识库还能不能用」的唯一判据。行数对但向量数为 0，意味着恢复出来的是一个查不到任何知识的空壳。

⚠️ **备份之后某个应用换过向量模型的话**，恢复出来的应用指针与向量会一起回到备份时的状态（二者同库，是一致的），检索可用；
但那次切换要重新做一遍。只有改过 `AI_EMBEDDING_DIMENSIONS` 的备份才真正不可用——维度对不上，启动时会直接拒绝。

## 10. 故障手册

这一节收录的都是**不会报错、只会静默表现异常**的故障——服务照常 UP、日志照常干净，只有知道去查哪张表才定位得到。

### 1. 对话与检索全线 404

**现象**：任何对话都失败；文档上传后一直停在「处理中」最后变 FAILED。

**查**：
```bash
# 环境变量里的端点
echo $AI_BASE_URL          # 必须以 /v1 结尾
# 库里存量模型行的端点
docker exec -i qingyu-postgres psql -U postgres -d qingyu_care -c \
  "SELECT id, name, endpoint FROM ai_model_config;"
```

**修**：两处都补 `/v1`。库里的行执行 `migration/2026-07-30-append-v1-to-model-endpoint.sql`（幂等，重复执行不会拼成 `/v1/v1`）。

### 2. 中文关键词检索与热点分析静默失效

**现象**：启动日志有 `混合检索表结构初始化失败，关键词检索可能不可用`（WARN 级，服务照常起）；效果分析的「热点」标签页永远空白。

**根因**：`init.sql` 只在数据目录为空时执行一次。升级到带 zhparser 的镜像后，**存量数据卷不会重跑它**。

**查**：
```bash
docker exec -i qingyu-postgres psql -U postgres -d qingyu_care -c "\dx"
# 应能看到 vector 与 zhparser 两个扩展
```

**修**（不必重建数据卷）：
```bash
docker exec -i qingyu-postgres psql -U postgres -d qingyu_care -c "
CREATE EXTENSION IF NOT EXISTS zhparser;
DO \$\$
BEGIN
    IF NOT EXISTS (SELECT 1 FROM pg_ts_config WHERE cfgname = 'chinese_zh') THEN
        CREATE TEXT SEARCH CONFIGURATION chinese_zh (PARSER = zhparser);
        ALTER TEXT SEARCH CONFIGURATION chinese_zh ADD MAPPING FOR n,v,a,i,e,l,j WITH simple;
    END IF;
END
\$\$;"
```
然后重启后端，日志应变成 `混合检索：vector_store.content_tsv 生成列与 GIN 索引已就绪`。

### 3. 知识库有内容但问什么都答不知道

**现象**：文档状态「已完成」、切分块数正常，但对话总是走兜底话术。

**查两处**：

```sql
-- ① 相似度阈值是不是太高（最常见）
SELECT id, name, scenario, similarity_threshold, tenant_id FROM chat_strategy;

-- ② 文档的租户字段是不是 NULL
SELECT id, name, status, chunk_count, tenant_id, app_id FROM document;
SELECT metadata->>'tenantId' AS 租户id, count(*) FROM vector_store GROUP BY 1;
```

**①** 阈值刻度依赖 embedding 模型。默认跟随向量模型的推荐阈值；若策略关掉了「跟随」、或推荐阈值本身没标定过，换过模型就要重新标定，方法见[使用手册第 6 节](./使用手册.md#6-问答策略topk相似度阈值兜底)。另查 `embedding_migration_job` 最近一条是否停在 `FAILED` / `INTERRUPTED`（切换挂起时检索仍用旧模型，新上传的内容两边都写，不影响检索）。

**②** 如果 `document.tenant_id` 为 NULL、或 `vector_store` 的 `tenantId` 是空串 `""`，那这些向量**对任何租户都检索不到**——不是「对所有租户可见」，而是恰好相反：检索条件拼的是 `tenantId == '<真实id>'` 等值匹配，空串永远匹配不上。这类数据只能重新摄取修复。

### 4. 回复不逐字出现，整段一次性刷出

**现象**：流式对话看起来像非流式；坐席端收不到实时消息。

**根因**：反向代理开着响应缓冲。

**修**：nginx 的 `/api/` location 里加 `proxy_buffering off;`（见 5.2）。用了 CDN 或云负载均衡的话，那一层通常也有独立的缓冲开关，要一并关掉。

### 5. 用量看板一直是 0

**不是故障**。token 计量是**开放 API 专属**，管理后台对话页不计量。用 `/open/v1/**` 打一次就有数据了。

### 6. 审计日志与 Webhook 投递莫名延迟几分钟

**根因**：长任务（文档摄取、站点爬取、向量模型迁移）掉进了默认线程池。默认池是 core 8 + **无界队列**，无界队列下 core 占满后 `maxPoolSize` 永不扩容，于是审计与 webhook 全排在长任务后面。

**查**：看是否有大批量摄取/爬取任务正在跑。正常情况下长任务走独立的 6 线程池，不会影响短任务。

### 7. 网页文档每轮同步都重新嵌入（悄悄烧钱）

**现象**：无任何报错，只是 embedding 账单持续增长。

**查**：
```sql
SELECT id, name, source_url, content_hash, last_synced_at, sync_failure_count
FROM document WHERE source_url IS NOT NULL;
```
`content_hash` 为 NULL 说明摄取成功后没落库，于是每轮同步都判定「内容变了」而重嵌。

### 8. Webhook 投递卡在 PENDING 永不成功

**现象**：投递行一直是 PENDING，目标服务却从没收到请求。

**根因之一**：**有另一个实例连着同一个 Redis**，共用消费组 `webhook-workers` 把消息抢走并 ACK，然后拿 deliveryId 去自己的库里查（查不到），于是消息就此丢失。本地开发时同时跑着 dev 后端与集成测试最容易撞上。

**查**：确认同一 Redis 上只有一套实例在消费，或各环境用独立 Redis。

### 9. 接入 MCP 服务时同步报错，工具一个都拉不下来

**现象**：MCP 服务页点「同步工具」直接失败，服务列表里那条一直是「尚未同步」。

**根因**：`mcp_tool.description` 存的是远端 server 自报的工具说明，长度由第三方决定。该列早期是 `varchar(1000)`，接入描述较长的公共 MCP server（如 context7）时 INSERT 直接被 PostgreSQL 拒绝。

**查**（预期 `text`，若是 `character varying` 就是没跑迁移）：
```bash
docker exec -i qingyu-postgres psql -U postgres -d qingyu_care -c \
  "SELECT data_type, character_maximum_length FROM information_schema.columns
    WHERE table_name = 'mcp_tool' AND column_name = 'description';"
```

**修**：执行 `migration/2026-08-22-mcp-tool-description-to-text.sql`。**升级到该版本后必须跑一次**——`ddl-auto: update` 只加列、不改已有列的类型，实体注解改了也不会动存量库，症状与升级前一模一样且启动期无任何提示。

### 10. SSRF 守卫在 fake-IP 模式的 DNS 环境下整体失效

**现象**：没有任何现象——这正是它的危险之处。工具 / MCP server 的 URL 指向内网主机名时本该被拒，却照常连上了。

**根因**：`SsrfGuard` 的判据是「把主机名解析成 IP，逐个检查是否属于环回 / 内网网段」。若宿主机的 DNS 处于 **fake-IP 模式**（Clash/Mihomo 等透明代理的默认行为，某些容器 DNS 代理也如此），**每个域名都会被解析成一个 `198.18.0.0/15` 的合成地址**——它不属于任何被拦网段，守卫放行，随后代理再把这个合成地址映射回真实目标并建立连接。实测：URL 填 `http://127.0.0.1.nip.io:8080/…` 时守卫放行，出站请求真的打到了本机 8080。

**查**（正常环境应返回真实公网 IP；返回 `198.18.x.x` 即为 fake-IP 模式）：
```bash
nslookup example.com
```

**修**：部署环境不要让应用容器走 fake-IP 模式的解析器——给后端容器配真实递归 DNS（compose 的 `dns:` 或宿主 `/etc/resolv.conf`）。这不是应用层能修的：DNS 撒谎时，任何基于 IP 的校验都不成立。

### 11. MCP 工具「调用失败」，但同一个 server 同步工具清单一切正常

**现象**：对话里模型调某个 MCP 工具，回来的是「工具调用失败」；服务页点「同步工具」却完全正常，工具列表也在。日志里是 `TimeoutException` 或 `ReadTimeoutException`。

**根因**：`mcp_server.timeout_ms`（界面上的「超时(ms)」，默认 10000）**是单次 MCP 请求的响应总时长上限**，不是连接超时。同步只发 `initialize` + `tools/list`，都是毫秒级往返，所以永远撞不上；而深度检索类工具单次跑十几秒很常见，必然撞上。⚠️ **远端持续吐进度也不豁免**——SDK 那层是总时长上限，与「相邻两次读的间隔」是两回事（后端 `McpTimeoutSemanticsTest` 用真实 TCP 时序把两层分别测过）。

**修**：调大该 server 的「超时(ms)」。参考量级：单次调用的实际耗时上限 ≈ `2×timeout_ms`（`initialize` 与 `tools/call` 是两次请求、各享独立一份）。⚠️ 别无脑往大调：MCP 调用在对话请求线程上同步阻塞，值越大，一个卡住的远端占住线程越久，也越容易顶穿前端与网关自己的超时。

### 12. 首页能打开但刷新子路由 404

**根因**：静态服务器没配 SPA 路由回退。

**修**：nginx 加 `try_files $uri $uri/ /index.html;`（见 5.2）。

### 升级流程

1. 备份数据库（见上）。
2. 检查 `backend/src/main/resources/migration/` 是否新增了需要手工执行的脚本。
3. 构建新版 jar（Widget 有改动时其产物已包含在 jar 内，客户站点无需变更嵌入代码）。
4. 替换 jar 重启后端（JPA 自动增量更新表结构）；重新发布 `frontend/dist`。
5. 验证：`/api/actuator/health` 为 UP，管理后台可登录，Widget 站点可正常对话。

回滚：换回旧 jar 即可（`ddl-auto: update` 只增不删，旧版本兼容新增列）；数据异常时用备份恢复。

## 11. 快速排查对照表

会明确报错的问题看这里；**不报错只静默异常的**看[第 10 节故障手册](#10-故障手册)。

| 现象 | 排查方向 |
|------|----------|
| 启动报 pgvector 相关错误 | 数据卷是否用本项目镜像初始化：`docker exec qingyu-postgres psql -U postgres -d qingyu_care -c "\dx"` 应能看到 `vector` 与 `zhparser` |
| 启动报 `vector_store.embedding 列类型为 vector(N)…不一致` | 改了 `AI_EMBEDDING_DIMENSIONS`。维度不能对已有库热切换：改回原值，或清空 `vector_store` 后重建该列并重新摄取 |
| 新应用上传文档全部失败、报「平台尚未配置可用的向量模型」 | 平台没有启用的向量模型（全被停用或删了）。在「共享模型 → 向量模型」里添加或启用一条 |
| 文档上传失败 | RustFS 是否健康（`:9000/health`）、bucket 是否存在（`createbuckets` 任务是否成功）、`STORAGE_*` 凭据是否正确 |
| Widget 站点 403 | 应用的 allowedOrigins 未包含该站点 Origin（**协议 + 域名 + 端口需完全一致**，上了 HTTPS 记得改成 `https://`） |
| 开放 API 429 | 触发应用级限流，按 `Retry-After` 重试或调高应用限流配置 |
| 开放 API 403 `QUOTA_EXCEEDED` | 租户月度额度用尽，升级套餐或等待月度自然重置 |
| 后端启动即退出，日志报端口占用 | 8080 被占，常见于上一个进程没退干净 |
| 前端页面白屏、控制台 401 后跳登录 | token 过期或后端重启导致会话失效，重新登录即可 |
