1. ~~**`@Async` 池是空壳默认池，长任务与关键短任务共享**~~ ✅ **已清理（2026-08-07）**
   现已分两池：短任务（用量计量/审计日志/webhook）留在 Boot 默认池，长任务（文档摄取/QA 生成/批量重嵌/网页同步/站点爬取）走 `AsyncConfig.LONG_TASK_EXECUTOR`（固定 6 线程 + 500 有界队列 + `AbortPolicy`）。`AsyncExecutorRoutingTest` 扫描全部 `@Async` 方法强制归类，新增长任务忘加 qualifier 会红。

2. ~~**token 多轮聚合计量少计**~~ ⚠️ **原描述有误，已核实推翻（2026-08-11）；残余风险窄到当前配置下不可能发生**
   2026-08-11 读 Spring AI 2.0 源码（`spring-ai-openai` / `spring-ai-model` 的 sources jar）逐条核对，结论与原描述**相反**：
   - **非流式不少计**。`OpenAiChatModel.internalCall(prompt, previousChatResponse)` 在工具多轮之间把上一轮响应传进递归，经 `UsageCalculator.getCumulativeUsage` **逐项相加**（`prompt`/`completion`/`total` 都加，previous 为 null 时才返回 current）。所以最终那个 `ChatResponse` 的 usage **本身就是跨全部轮次的总量**，`getTotalTokens()` 取它是对的。
   - **流式取末值也是对的**。`internalStream` 传给 `getCumulativeUsage` 的 previous 是 `null`，且它内部**没有**工具执行递归；单轮流式只有末尾 chunk 带 usage，`tokens.set(...)` 取末值恰好正确。
   ⚠️ **按原描述去「改成累加」会让计费变得更糟**——非流式每轮的值已含前几轮，再累加就是**重复计费**。这个坑已写进 `ChatServiceImpl.meterContentStream` 的 javadoc，免得下一个人照清单动手。
   **残余风险（窄）**：流式且真的发生多轮工具调用时无跨轮累计。本项目走不到——Qwen 分帧发 tool_call 会先把上游 `ChunkMerger` 打挂，`streamChat` 因此降级到非流式重跑（见 §5.4 与 CLAUDE.md），而非流式是累计的。**换用不触发该上游缺陷的供应商时这条必须重新评估**，届时的验收只能靠真机：挂一个工具并触发它，查 `sys_api_usage.token_count` 是否等于各轮之和。
   <details><summary>原描述（已证伪，保留以防有人照它动手）</summary>
   `ChatServiceImpl` 里是 `tokens.set(...)` 覆盖而非累加，非流式同样只取单个 response 的 usage。带工具时 Spring AI 内部跑多轮，只记末轮。详见 §5.4 第 8 项。
   ⚠️ 未上线前实际损失为零，而修法可能要接管 Spring AI 的工具循环（关 `internalToolExecutionEnabled` 自驱多轮，或走 observation 拦截累加）——属「看着小其实不小」，别低估。
   —— 这段很可能是照 Spring AI **1.x** 的行为写的，Boot 4.1 + AI 2.0 迁移之后没有重新核对过。
   </details>

11. ~~**`@Builder.Default` 字段在局部 PUT 时被静默重置成类默认值**~~ ✅ **已清理（2026-08-13）**
   八个控制器、九个端点（`PlatformController` 一个文件里有两个：`updateSharedModel` /
   `updateSharedTool`）全部改用专用 `*UpdateRequest` DTO（`dto/` 下 7 个类，`PlatformController`
   的两个 update 复用工具与模型的 DTO）。DTO 一律不写字段初始化器——**根源是字段初始化器
   本身，不是 `@Builder.Default` 注解**（实测 `KnowledgeBaseRequest` 有初始化器无
   `@Builder.Default`，`new` 出来照样带默认值，见 `PartialUpdateSemanticsTest` 里的反证测
   试），`null` 才真正表示「请求体没给」。`UserController` 一并从 `Map + containsKey` 统一
   成 DTO。
   同批修掉一个活缺陷：编辑用户时前端提交空串密码 → 后端 `BCrypt.hashpw("")` → 用户被彻底
   锁死（旧密码登不上，空密码被 `@NotBlank` 拒）。后端改为 `!= null && !isEmpty()`；前端
   `UserListPage.tsx` 编辑提交时也不再带上空密码字段，作为第二道防线——两道互为兜底，
   后端那道不能因此去掉，它要防的是任何调用方（第三方 API 调用、其他前端页面），不只是
   这一个页面。
   `PartialUpdateSemanticsTest` 9 条测试 + 四次变异验证守住。详见
   `docs/superpowers/specs/2026-08-13-update-dto-partial-put-design.md`。
   ⚠️ **残留盲区**：`PlatformController` 另两处同款判空（`updateSharedModel` 的 `apiKey`、
   `updateSharedTool` 的 `authHeader`）代码本身是对的，但零测试守护——改回只判 `!= null`
   不会有任何测试转红，另立第 13 项。
   <details><summary>原问题</summary>
   位置：`AiToolController.update`、`AiModelController.updateModel`、`PlatformController.updateSharedTool`（平台共享工具批新增的第三处，复制了同一形态）。
   机制：这些方法用 `if (field != null) existing.setXxx(...)` 做「空值不覆盖」。但 Lombok 的
   `@Builder.Default` **会把默认值也应用进无参构造**（已用字节码确认：`AiTool()` 里
   `invokestatic $default$timeoutMs → putfield`），而 Jackson 反序列化走的正是那个无参构造

   **类默认值而非 null**，`!= null` 恒真，于是把库里的值覆盖掉。
   **可达性（这条务必写对）**：`frontend/src/pages/ToolConfigPage.tsx` 的 `handleToggle` 就是
   `aiToolService.update(t.id, { enabled: !t.enabled })`——**租户在工具卡片上点一下启用/停用
   开关即触发**，该工具的 `httpMethod` 被静默改回 `GET`、`timeoutMs` 回 5000、
   `maxResponseChars` 回 4000。一个配好的 POST 工具就此变成 GET，无任何提示。**不是**「只有
   直接构造部分 JSON 的 API 调用才会中招」。
   定性：既有缺陷（`handleToggle` 早于平台共享工具这批改动），非本批引入，但本批把同一形态
   复制了一份（`PlatformController.updateSharedTool`）。
   </details>
