# 轻语（QingYu Care）开发流程文档

> 适用范围：本文档面向参与开发的工程师，覆盖环境搭建、日常开发流程、分支与提交规范、测试体系与各子项目的开发约定。
> 部署与上线请看 [`部署文档.md`](./部署文档.md)；架构细节与易错陷阱的权威说明在根目录 [`CLAUDE.md`](../CLAUDE.md)。

## 1. 开发环境准备

| 依赖 | 版本 | 用途 |
|------|------|------|
| JDK | 17 | 后端 |
| Maven | 3.9+ | 后端构建 |
| Node.js + pnpm | 18+ | 前端 / Widget（统一用 pnpm，勿用 npm/yarn） |
| Docker Desktop | - | 基础设施 + 集成测试（Testcontainers） |
| DashScope API Key | - | 后端启动必需（环境变量 `DASHSCOPE_API_KEY`） |

## 2. 本地启动

```bash
# 1. 基础设施（PostgreSQL + RustFS + Redis）
cd docker && docker compose up -d

# 2. 后端（http://localhost:8080/api，Swagger: /api/swagger-ui.html）
export DASHSCOPE_API_KEY=your-key
cd backend && mvn spring-boot:run -Dspring-boot.run.profiles=dev

# 3. 前端（http://localhost:5173，/api 自动代理到 :8080）
cd frontend && pnpm install && pnpm dev

# 4. Widget 本地调试（可选，独立子项目）
cd widget && pnpm install && pnpm dev
```

首次启动后端会由 JPA `ddl-auto: update` 自动建表，无需手工执行 SQL。

## 3. 分支与提交规范

- **默认分支 `master` 不直接提交**：从 `master` 切出特性分支开发，完成并验证后合回。
- 分支命名：`<type>/<主题>`，如 `feat/webhook-queue`、`fix/tenant-guard`、`docs/deploy-guide`。
- 合并采用 **`--no-ff` merge**，合并提交信息以 `merge: ` 为前缀概括本次改动。
- 提交信息**全部使用简体中文**，格式沿用仓库既有风格：

```
<type>(<scope可选>): <一句话中文描述>

type: feat | fix | refactor | test | docs | chore
示例:
  feat: Webhook 投递 Redis Stream 队列化（消息队列落地）
  fix(frontend): 清理 react-hooks lint 问题
  merge: 管理后台菜单深度分组重构
```

- 代码注释同样使用简体中文。
- 推送远端 / 发 PR 前确认第 7 节「提交前检查清单」全部通过。

## 4. 功能开发流程

较大的功能沿用「先设计后实现」的既有惯例：

1. **对齐路线图**：确认需求在 [`SaaS平台规划.md`](../SaaS平台规划.md) 中的位置与边界。
2. **写设计文档**：`docs/superpowers/specs/YYYY-MM-DD-<主题>-design.md`（背景、方案、接口、数据模型、边界情况）。
3. **写实现计划**：`docs/superpowers/plans/YYYY-MM-DD-<主题>.md`（拆任务、排依赖）。
4. **切特性分支实现**：测试先行（先写失败的测试再实现，尤其是服务层逻辑）。
5. **回归验证**：`mvn test` → `mvn verify`（涉及后端）、`pnpm lint && pnpm build`（涉及前端）。
6. **合回 master**，并回填规划文档的完成状态。

小改动（bugfix、文案、重构）可跳过 1–3，直接特性分支 + 测试。

## 5. 后端开发约定

### 5.1 分层与结构

- 包结构：`controller` / `service` / `repository` / `entity` / `dto` / `config` / `event` / `scheduler` 等，对外开放 API 独立在 `controller/open` 与 `dto/open`。
- **只有复杂服务（`ChatService`、`KnowledgeService`）用接口 + `service/impl` 拆分**；其余服务直接写单个 `@Service` 具体类，不要为简单服务强行加接口。
- DTO 转换用**手写静态工厂**（如 `OpenChatResponse.from(...)`），不用 MapStruct。
- 统一响应 `dto/ApiResponse`、分页 `dto/PageDTO`；业务异常抛 `BusinessException` / `ResourceNotFoundException` / `OpenApiException`，由 `GlobalExceptionHandler` 统一处理（注意：`BusinessException` 返回 HTTP 200 + 业务 code，前端按 code 判断）。
- 写操作加 `@AuditLog(action=, targetType=)` 注解即可自动落审计日志（异步 + 敏感字段脱敏）。

### 5.2 多租户开发注意事项（最容易踩的坑）

完整机制说明见 `CLAUDE.md`「多租户隔离」，开发时牢记：

1. **业务实体默认继承 `BaseTenantEntity`**，租户/应用过滤与写入回填全自动——前提是请求经过 `TenantInterceptor`（真实 HTTP 请求）。
2. **`findById` 不走 Hibernate `@Filter`**（Hibernate 6 限制）：任何「按 id 取单条再操作」的服务方法必须接入 `TenantOwnershipGuard` 做显式归属校验，否则就是越权漏洞。新增服务一律接入。
3. **异步/跨线程写入的实体不能继承 `BaseTenantEntity`**（`@Async` 线程没有 `TenantContext`）：参照 `WebhookDelivery` / `SysAuditLog` / `SysApiUsage`，持有显式 `tenantId` / `appId` 字段并在业务侧赋值。
4. **平台默认配置（`tenant_id IS NULL` 行）对租户查询不可见**：`ChatStrategy` / `PromptTemplate` / `AiModelConfig` / `HandoverRule` 的回退链路必须用原生 SQL 绕过过滤器。新增「平台可共享 + 租户可覆盖」的配置实体时复刻这套回退，并注意平台行仅平台管理员可写。
5. **bulk UPDATE 与平台管理员的 `findAll` 不受 `@Filter` 保护**，需要显式加范围条件。

### 5.3 核心链路改动须知

- RAG 对话链路（`ChatServiceImpl`）串联 策略 → 检索 → Prompt → 模型路由 → 转人工判定 → 流式计量，改任一环节先通读全链。
- **token 计量是开放 API 专属**：计量回调 `onTokensUsed` 由 `OpenChatController` 注入，不要把计量逻辑塞进 `ChatServiceImpl` 内部。
- Webhook 语义边界：**DB 投递行是事实源**（至少一次保证），Redis Stream 队列只做加速分发，消费侧先 ACK 再投递。改动投递链路时不能破坏这个不变量。
- 改动配置回退相关服务后，务必跑 `mvn verify` 让 `*FallbackIT` 守护链路过一遍。

## 6. 测试体系

两层测试由 Maven 插件按命名自动切分（配置见 `pom.xml`）：

| 层级 | 插件 | 命令 | 约定 | 依赖 |
|------|------|------|------|------|
| 单元测试 | Surefire | `mvn test` | 纯 Mockito（`@ExtendWith(MockitoExtension.class)`），不起 Spring 容器 | 无需 Docker |
| 集成测试 | Failsafe | `mvn verify` | 类名 `*IT`，放 `it/` 包，继承 `support/AbstractPostgresIT`（Testcontainers 起单例 pgvector 容器） | 需 Docker Desktop |

```bash
mvn test  -Dtest=ConfigServiceTest                                # 单个单测类
mvn test  -Dtest=WebhookSignatureTest#signs_body_with_hmac_sha256 # 单个方法
mvn verify -Dit.test=OpenApiAuthIT                                # 单个 IT（注意是 it.test）
```

写测试的原则与坑：

- **新增测试优先写单测**；只有跨组件行为（鉴权链路、多租户过滤、DB 语义）才写 IT。
- 多租户过滤器只在**真实 HTTP 请求**流经 `TenantInterceptor` 时生效：IT 播种数据要么走 MockMvc 请求，要么用不继承 `BaseTenantEntity` 的实体；播种配置类数据须 `tenantId` + `appId` 双设。
- IT 基类提供 `seedApp(...)` 播种租户 + 应用；跨测试上下文注意清理种子数据。
- 慎用 `@MockitoBean` 替换 `VectorStore` 等共享 Bean——会破坏共享容器上下文缓存。
- 知识库摄取全链路（S3 + Embedding）**不写 IT**（外部依赖过重，已明确决策）。

## 7. 前端开发约定

- **HTTP 一律走 `api/client.ts` 的单例 axios**：它负责注入 `satoken` 与 `X-App-Id`、拆 `ApiResponse.data`、401 跳登录。新领域接口在 `api/` 下建对应 service 文件。
- 状态用 Zustand（`stores/`）；「当前应用」存 `appStore`，其 `id` 就是请求头 `X-App-Id` 的来源。
- 路由守卫：登录态用 `<ProtectedRoute>`；应用级配置页额外包 `<RequireApp>`；侧边导航按 `user.role` 过滤（`MainLayout.tsx`）。
- UI 组件用 `components/ui/` 的 shadcn 风格封装（CVA + `cn()`），路径别名 `@/` → `src/`。
- React hooks 规范：mount-only 的 `useEffect` 按项目惯例用 `eslint-disable-next-line react-hooks/exhaustive-deps` 注释；取数函数用 `async function` 声明（利用提升）而非 `const` 箭头函数，避免 immutability 违规。
- 提交前：`pnpm lint && pnpm build`（`tsc -b` 类型检查包含在 build 里）。

## 8. Widget 开发约定

- `widget/` 是独立 Vite 子项目（库模式，产出单文件 IIFE）。
- **`pnpm build` 直接输出到 `backend/src/main/resources/static/widget.js`，该产物提交进仓库**——改动 `widget/src/` 后必须重新 build 并连同 `widget.js` 一起提交，否则线上 Widget 不会更新。
- `.gitattributes` 强制 `widget.js` 为 LF 行尾，保证跨平台 diff 稳定，勿改。
- 单测：`pnpm test`（vitest + jsdom）。

## 9. 提交前检查清单

按改动范围勾选执行：

- [ ] 后端改动：`mvn test` 通过；涉及鉴权/多租户/配置回退/Webhook 时 `mvn verify` 通过（需 Docker）。
- [ ] 新增「按 id 操作」的服务方法：已接入 `TenantOwnershipGuard`。
- [ ] 前端改动：`pnpm lint`、`pnpm build` 通过。
- [ ] Widget 改动：`pnpm test` 通过，已重新 build 并提交 `widget.js`。
- [ ] 提交信息为简体中文且符合 `type(scope): 描述` 格式。
- [ ] 大功能：`docs/superpowers/` 的 spec/plan 与 `SaaS平台规划.md` 状态已回填。
